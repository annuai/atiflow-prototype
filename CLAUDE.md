## 1. What we are building

A real-time **3D robot fleet dashboard** for factory/warehouse floors. A client's CAD floor plan (DWG) becomes a Three.js scene you can orbit, pan, zoom and **walk through**. Ati Robotics AMRs run on it, driven by robot telemetry. It is **not** a workflow builder. We reuse only the *page layout and design language* of the Figma "Workflow Builder" screen.

Core promises:
1. **Any client DWG -> scene** through a repeatable import pipeline plus a per-site config, not hand-coded geometry.
2. **Robot data -> visuals** through one telemetry schema. Swapping mock for live data means writing one adapter.
3. **The renderer never knows about DWG, and the UI never knows about Three.js.** Three layers, each replaceable.

## 3. DWG facts (measured, first site)

- Whole-site plan: ~480k entities (LINE 294k, ARC 25k, LWPOLYLINE 20k, SPLINE 9k, INSERT 3.3k, TEXT/MTEXT 2.5k), 94 layers, no model/paper-space separation worth using, `$INSUNITS = 0` (unitless). Coordinates are **millimetres** (a bay is ~55,000 wide).
- It contains several buildings/drawings. The SMT production hall is the block at roughly **x 485,000-552,000, y 145,000-270,000 mm**, split into 3 bays (SMT lines at the south, assembly/workstations in the middle, ASRS + prep at the north).
- Useful layers: `WALL`, `A-WALL`, `50 MM EXTERNAL PILLAR`, `FAB WALL PANEL-*`, `EEC`, `EEC-1` (zone/area/equipment labels such as SMT OVER-L3..L12, PCBA WIP, THT WIP, VSTORE - ASRS, PREPARATION AREA, one `AMR` label), `AM_6`, `AM_8`, `A-EQUIP`, `0` (workstation blocks), `PATH`.
- Noise to drop by default: `LAYER01` (188k), `Sichtbar (ISO)` (116k), dimensions, hatches, MEP (`LAN`, `POWER`, `PNUEMATIC`, `PVC Conduits`, `NETWORK`), text notes.
- **The DWG has no AMR routes, stations or charging docks.** The nav graph must be authored or derived (see 6.3).
- Toolchain: `brew install libredwg` (already installed here), then `dwg2dxf` converts DWG->DXF, then Python `ezdxf` reads it. `dwgread -O json` works but produces ~730 MB, so avoid it. `dwg2dxf` warns about `DIMASSOC`/`ACDB_BLOCKREPRESENTATION_DATA`; these are harmless.
- Blocks (`INSERT`) hold much of the equipment detail (`workstation 1 meter`, `700 mm conveyor`, `VI 3D SPI`, hashed `A$C...` blocks). Some inserts reference missing block definitions (ezdxf raises `DXFStructureError`), so always wrap per-entity work in try/except and never call `bbox.extents` on the whole modelspace.


## 5. Conventions that must not drift

**Units and coordinates**
- Site frame = **meters**, X east, Y north (plan view), origin at the site's SW corner after crop. Heading `theta` in radians, 0 = +X, CCW.
- Three.js frame: `three.x = x`, `three.z = -y`, `three.y = up`. Convert in exactly one place: `core/coords.ts` (`toScene`, `fromScene`). Do not hand-convert elsewhere.
- DWG mm -> meters happens only in the importer (`scale` in config, default 0.001).

**Layout schema (`site.json`)** (all geometry already in meters, plain polylines)
`{ schema:1, siteId, name, units:'m', bounds:{minX,minY,maxX,maxY}, floorPolygons[], walls[{pts,height,thickness,kind}], pillars[{x,y,w,d}], zones[{id,name,kind,polygon,color,active}], equipment[{id,kind,label,x,y,w,d,h,rot}], doors[{x,y,w,rot}], labels[{text,x,y}] }`.
Size budget: target < 3 MB gzip. Importer must simplify (Douglas-Peucker, merge collinear, dedupe) and reduce thousands of lines to wall *extrusions* and instanced boxes. The runtime draws with `InstancedMesh` and merged geometry, never one mesh per DWG entity.

**Nav schema (`nav.json`, schema 2: rules + lanes, see section 12)**
`{ schema:2, siteId, nodes[{id,x,y,kind}], lanes[{id,from,to,geom:[x,y][],fleets[],speed,len}], stations[{id:'STA-101',name,nodeId,type,zone,fleets[]}], fleets[{id,name,color,areas[]}], trafficZones[{id,name,capacity,fleets[],polygon}], forbiddenZones[{id,name,reason,polygon}] }`. A lane is ONE direction only; opposite directions are separate paired lanes (keep-right). Robots move only along lanes of their own fleet. Pathfinding is Dijkstra over directed lanes in `core/lanes.ts`.

**Robot telemetry (the one contract everything maps through)**
```ts
type RobotState = 'idle'|'moving'|'working'|'charging'|'blocked'|'error'|'offline'|'paused';
interface RobotTelemetry {
  id: string;            // e.g. "AMR-007" (the Live Floor robots are named AMR-001, AMR-002... like the ones in the configurator)
  model: string;         // key into the robot model registry, e.g. "sherpa-xt-lite"
  fleetId: string;
  siteId: string;
  pose: { x:number; y:number; theta:number };   // meters / radians, site frame
  speed: number;         // m/s
  state: RobotState;
  battery: number;       // 0-100
  payload?: { kind:string; qty?:number } | null;
  task?: { id:string; type:string; from?:string; to?:string; progress?:number } | null;
  path?: {x:number;y:number}[];                 // planned route, optional
  currentNode?: string; nextNode?: string;
  alerts?: { code:string; severity:'info'|'warn'|'critical'; msg:string }[];
  ts: number;            // epoch ms from source
}
```
Rules: adapters emit `RobotTelemetry` only (translate vendor payloads inside the adapter). The store keeps latest + short history. The renderer **interpolates** between ticks (dead reckoning on `speed` and `theta`) so 1 Hz data still looks smooth. Unknown `model` falls back to the default robot. Stale `ts` (> N s) shows as `offline`.

**State -> visual mapping** lives in one table (`engine/robots/stateStyle.ts`): moving = teal sensor pulse, working = amber beacon, charging = green pulse + dock link, blocked = red pulsing ring (as in reference), error = red + alert pin, offline = grey/translucent, idle = dim sensor. Selected = teal pulsing halo.

**Robot models.** All robots are Ati Robotics AMRs. Registry `engine/robots/registry.ts` maps `model` -> `{ glb?, procedural(), footprint, label }`. Start with a procedural Ati-style body (original design, not the reference's box robot) so the system works with zero assets, and accept `.glb` drop-ins per model. Confirmed: procedural Ati AMR first (Figma mentions **Sherpa XT Lite**), GLB drop-ins later. `src/engine/robotMesh.ts` now follows the user's reference (side illustration + KeyShot render): Ati yellow `#fcd900` hip-roofed body, black bumper skirt, dark roof plate, lidar mast with orange beacon, red e-stop, side door + vent slits, black front panel with green lights, grey wheels, 'Ati SHERPA XT LITE' decal; a teal LED band under the body shows robot state. All models (`sherpa-xt-lite`, `sherpa-tug`) share that look. Dev-only `window.__engine` exists for debugging. **[OPEN]**: full model list when more are needed.

## 6. Key subsystems

### 6.1 DWG importer (`tools/dwg-import`)
Pipeline: `dwg2dxf` -> ezdxf scan -> **classify** each entity by layer/block regex from `import.config.yaml` -> crop to `bbox` -> explode only whitelisted inserts -> simplify -> write `site.json`. Config per site declares: `crop`, `scale`, `origin`, `layers:{wall:[...], pillar:[...], zone:[...], equipment:[...], ignore:[...]}`, `blocks:{'workstation 1 meter':{kind:'workstation',h:0.9}, '700 mm conveyor':{kind:'conveyor',h:0.8}}`, default heights per kind, `labelPatterns` (e.g. `^SMT`, `ASRS`, `PCBA WIP` -> zones). A `--preview` flag writes a PNG so a human can check the crop. For a new client: run with `--discover` to dump layer/block/text stats, write the config, rerun. **No client-specific code in the engine.**

### 6.1b Scope: whole building, active areas only (confirmed)
The **entire building is rendered** for context (walls, pillars, big equipment, outer halls), but only **active areas** are interactive. An active area = a zone where robots actually move (first site: the SMT hall and its bays). Rules:
- `site.json` zones carry `active: boolean`. Active zones are derived from `nav.json` (any zone containing graph nodes/edges), and can be overridden in `import.config.yaml` (`activeZones`).
- Inactive areas: dimmed/desaturated, no hover, no click, excluded from raycast (`layers`/`raycast` filter), no labels beyond the building name.
- Active areas: hover highlight, click -> camera flies to the zone, zone becomes the "current area" in the UI (breadcrumb + robot list filtered to it). Click empty space or Esc returns to the whole-building view.
- Walk mode works everywhere (collision applies); only *selection* is limited to active areas and robots.
- Performance: whole building is mostly static, so merge static geometry per area, use `InstancedMesh`, freeze matrices, and keep detailed equipment only in/near active areas (LOD by distance).

### 6.2 Scene (`engine/scene`)
Floor + subtle grid, extruded walls, pillars, equipment as instanced boxes colored by `kind`, zone floor tints + floating labels, optional ceiling/roof hidden by default (so top and orbit views are clear). Lighting: hemisphere + one shadowed directional; soft shadows only near the camera for performance. Layer toggles: Robots, Routes, Stations, Zones, Labels, Equipment, Heatmap.

### 6.3 Navigation (superseded by section 12 for lanes, fleets, traffic and forbidden zones)
First site (confirmed): I derive candidate aisles from free corridors between equipment, author `nav.json` with stations at ASRS, workstations and SMT lines, and the user corrects it through the overlay. The runtime is agnostic to how `nav.json` was produced (hand-made, derived, or client-supplied). A debug overlay draws the graph so it can be edited visually; later an in-app edit mode can export `nav.json`.

### 6.4 Camera modes (`engine/camera`)
- **Orbit** (default): LMB-drag orbits, **MMB-drag pans in screen space (like DCC tools; browser middle-click auto-scroll is suppressed)**, RMB-drag also pans, wheel zooms to cursor, polar clamp so it never goes under the floor (if a pan would sink it, camera and target are lifted together so a pan stays a pure translation). Only the primary button selects robots/stations/zones; MMB/RMB are camera-only.
- **Top**: orthographic-like plan view with 2D feel, for map-style tracking.
- **Walk**: pointer-lock first person, WASD + mouse look, eye height 1.7 m, simple collision against wall/pillar/equipment AABBs (grid-based broadphase), Shift = run, Esc exits. Touch: virtual stick.
- **Follow**: chase camera locked to the selected robot.
Zoom control (+/-/percent), Home, Top/Orbit/Walk switch (the Figma Map Preview card was dropped by user decision).

### 6.5 Adapters
`interface TelemetryAdapter { connect(): void; disconnect(): void; onTelemetry(cb); onFleetMeta(cb) }`.
- `MockSimulator`: runs N robots over `nav.json` with tasks, pauses, charging, random blocks/faults, battery drain. Deterministic with a seed. This is the default until a live feed exists.
- `WebSocketAdapter` / `RestAdapter`: map vendor JSON -> `RobotTelemetry` via a small mapping function. Config in `public/config.json` (`adapter`, `url`, `siteId`).
- Replay mode (the Figma "Simulate" button's slot): record/replay telemetry JSONL.

## 12. Map rules: fleets, lanes, traffic zones, forbidden zones (user spec, this session)

**Rules the system must show and never break**
1. **Fleets are limited to map areas** (`fleets[].areas` = site zone ids). A fleet cannot leave its areas. Fleets are isolated unless an area is listed by two fleets (a *shared* area, e.g. ECC `east-strip`); that is the only place robots meet other fleets. Lane network, station ownership and routing all respect this.
2. **One lane, one direction, always.** Every aisle has two paired lanes (one per direction, keep-right offset 0.5 m). No bidirectional lanes exist.
3. **Traffic zones**: a robot stops at the zone entrance (hold point 1.8 m before) until fewer than `capacity` robots (default 1) are inside, FIFO queue, applies across fleets. 
4. **Forbidden zones**: robots never enter; the deriver removes lanes/stations from them.
In real life the robot's localization and mapping engine enforces this; the dashboard only **visualises** it and **independently verifies** it from reported poses.

**Where it lives**
- `tools/dwg-import/derive_lanes.py <site.json> <import.config.yaml> <nav.json> [--preview png] [--force]`: free-space -> skeleton (aisle centre-lines) -> graph -> stations (on-lane or spur) -> fleet assignment -> paired lanes -> sample traffic zones at junctions -> validation (every station reachable by each owning fleet, no lane inside a forbidden zone; exits 1 on error). Config keys `fleets`, `forbidden`, `lanes` in `import.config.yaml`. **Fleet areas, forbidden zones and traffic-zone placement for ECC are SAMPLE data**; replace with the client's real map rules (edit config + rerun, or edit nav.json directly).
- `src/core/lanes.ts` LaneGraph (route + path geometry), `src/core/rules.ts` RulesIndex (independent checker + traffic occupancy), `src/adapters/sim.ts` FleetSim (pure deterministic simulator obeying all rules), `src/adapters/mock.ts` real-time wrapper.
- `src/engine/rulesLayer.ts` draws lanes (fleet colour, shared = indigo, direction arrows), traffic zones (amber; orange occupied; red + pulse when robots wait; magenta over capacity; label `TZ-xx · 1/1 · 2 waiting`), forbidden zones (red hatch + barrier + `NO-GO` label), stations (pin + `STA-1xx` label, clickable).
- UI: one popup card `src/ui/InfoPanel.tsx` is used by BOTH `RobotPanel` and `StationPanel` (title, subtitle, status pill, fleet chips, stat grid, custom children, alerts, actions). Reuse it for any new selectable thing. `MapLegend` shows the key plus live counters (traffic zones occupied/waiting, rule violations).

**Telemetry additions (adapters must fill these from the robot/fleet manager)**: `laneId`, `traffic:{zoneId,status:'waiting'|'inside'}`, `waitReason`, `atStation`, `task.to` = station id (`STA-xxx`). New state `waiting` (purple) = holding for a traffic zone or headway. Rule alerts (`FORBIDDEN_ZONE`, `FLEET_BOUNDARY`, `OFF_LANE`, `WRONG_WAY`, `TRAFFIC_VIOLATION`) are computed in the store (`ingest`) from poses, so they show even if the robot reports nothing; they raise red ring, popup alert, event feed and the violations counter.

**Station naming**: ids `STA-101...` assigned by the deriver (sorted by area, then position); `name` is the real name from the drawing labels (duplicates numbered, e.g. `PCBA WIP 2`), plus placeholder `Assembly Workstation n` and `Charging Dock n`. Clicking a station opens the popup: actual name, type, map area, serving fleets, docked robot, incoming bots with ETA/distance, status (Free / Robot inbound / Occupied / Charging).

**Traffic rules, from the Ati Documentation System (`Ati-documentation-system/content-md`: traffic-control, v-visa, v-resource-reservation, v-deadlock, v-priority, v5-waypoint-routing):** VISA is first-in-first-out approval: the first robot to arrive at a hold point is granted the visa, the others wait *outside* the zone, and the visa is given back when the robot has cleared the area (not when its trip ends). **What did not help (measured on 6 seeds x 10 simulated minutes, `scratchpad` bench):** lane-pair sharing of an intersection, capping permit groups, congestion-weighted routes and a preference for spur stations all made waiting longer; first-in-first-out tickets and the deadlock detector helped.

On the road a robot can only take another road to the same destination, hand over permits it holds, or wait (`redirect()` and dropping an unreachable destination were removed). Waits carry the reason and who is first: telemetry `waitsOn[]` plus alerts `INTERSECTION_WAIT` ("Waiting for the intersection to clear (AMR-008 first)"), `HEADWAY_WAIT` ("Queued behind AMR-004") and `TRAFFIC_WAIT`; the Dashboard (new) attention list shows the same text. **Why long waits happened (measured, not assumed):** (1) grouped permits are long on this map (median 12 m / 5 intersections per request, 90th percentile 27 m / 11; one robot held 23 at once), but capping the group length made waits much WORSE (58-61% of robot time in waits > 2 min) and switching grouping off barely changed anything, so grouping is not the main cause; (2) with trips locked in, rings of robots at a station (one leaving, one arriving head-on, a third holding the traffic zone) stayed stuck for ever, which only a swap of the not-yet-started trip can break; (3) the circle chains that model robots were about 3 mm short of the real 1.2 x 0.85 m bodies on diagonals (a hairline touch), fixed with `ROBOT_R` 0.435 / `TROLLEY_R` 0.375 (bigger margins, 2 cm or more, triple the waiting because lanes are only ~1 m apart), and a stopped robot only rotates when its swung corners are clear. 12 seeds x 20 min: 7.0% of robot time in waits > 2 min.

**Lane joins (user request):** `core/lanes.ts` no longer joins consecutive lanes with a straight connector between their raw end points (which overshot the junction and doubled back, drew crossing lines and little diamond loops, and forced near-U-turns that robots could not follow). Each lane is cut short at the junction (`SETBACK_JUNCTION` 1.5 m where 3+ lanes meet, `SETBACK_BEND` 1.0 m at a simple bend, at most 45% of the lane, nothing at a dead end) and every turn is ONE smooth cubic curve (`turnCurve`) from the end of one lane to the start of the next with matching directions. `LaneGraph.plan()` drives exactly that geometry (a robot already part-way along its first lane carries on from where it is, and when it is already inside the cut-off part the turn starts right there); the map draws `roadLanes()` (lanes cut at junctions) plus `connectors()` (one curve per turn; no turn back into the paired lane except at a dead end). Intersections are still derived from the raw lanes (`smoothLanes()`). Result on the 12-seed benchmark: 4.3% of robot time in waits > 2 min (7.0% before), about 19% more trips finished, no touching, no rule violations. Tested in `tests/laneJoins.test.ts` (no step goes back on itself, no kinks, part-way plans carry on from the robot). A simulator note: a robot must not slide sideways, so a stopped robot only rotates when its swung corners are clear; making robots stop and pivot at any large heading difference was tried and froze the fleet.

## 36. Essential Fleet KPIs (user request: the KPI board; contract, measurement log, formulas)

Reliability: Deadlock frequency, Mean time between failures, SLA compliance, Charging availability (the board's description stickies sit one column left of their titles; matched by meaning). Dev handle `window.__measurements`.
**Known limits:** only "Today" is measured and only for the time the feed has run in this browser session; other periods are sample data (labelled); the simulator is much busier than a real floor (about 10 trips per robot-hour, deadlock rings 10 per hour) so absolute values are not factory numbers; SLA deadline and battery capacity are placeholders. ## 70. A traffic zone at every junction (user request; supersedes the sample zones of section 12 and the invisible intersections of sections 26-27)
**What:** every junction of a lane map (where lanes of different flows meet, cross or split) is now a **traffic zone** of capacity 1, drawn on the map (ECC: 60 zones, was 15 samples). Nothing is planned ahead: a robot asks for a zone when it reaches its hold point; if another robot is inside, it waits there until that robot (and its trolley) has left, first come first served; then the next goes. **Where they come from:** `core/junctions.ts` `junctionZones(graph, margin = 1.2, mergeGap = 2 * margin)` (the junction clusters of `Intersections.areas()`, each grown by `margin` metres into a convex area; junctions whose areas would overlap are one zone), written into `nav.json` by `npm run derive:zones -- public/sites/<id>/nav.json` (`tools/derive-zones/derive-zones.ts`; run it after `derive_lanes.py`, which still writes SAMPLE zones, or after the lanes change; `tests/junctions.test.ts` fails when `nav.json` and the lanes disagree). **The simulator** (`adapters/sim.ts`) now uses the nav's traffic zones as its ONLY junction control (the invisible `Intersections` permits and their same-lane sharing are gone from it; `Intersections` remains for the map audit and for drawing the zones): strict capacity 1, hold points on road outside every zone with the robot AND its trolley clear (`placeHolds`; two zones with no such place between them are taken together), a robot standing inside a zone at the start of its trip and asking for it goes first (`leavingFirst`), and a robot's own reserved way no longer blocks a robot right behind it that waits for it (the trolley's current position is not swept). **Recorded exception:** to break a deadlock a zone holder can hand its zone over (the old recovery step); that robot reports the warning `ZONE_HANDOVER` while it is still inside and the independent checker (`RulesIndex.traffic`) does not count it as a second robot in the zone. The checker counts a robot as in a zone when it drives through (speed >= 0.05) or reports `traffic: inside`; a robot standing at a station or hold point inside the area is not "in traffic" (its body blocks the others physically). Telemetry `traffic` now carries the zone id for waiting and inside; waits show `TRAFFIC_WAIT` ("Waiting for TZ-xx"). Small test maps (`tests/helpers/maps.ts`) get their zones from `junctionZones` too. **Measured** (6 seeds x 10 simulated minutes): 0 robots in a zone together, long waits (> 2 min) 11% of robot time and 308 trips, against 7.6% and 320 for the old sample-zone + hidden-intersection design: some extra waiting is the price of one robot per junction; all sim tests pass (12 seeds x 20 min under 14% long waits, zero violations). **Known limits:** zones are drawn from the lanes and the robot body, not surveyed; a few stations sit inside junction zones (a robot parked there blocks that zone physically); one seed can still leave a pair of robots waiting for each other for minutes (recovery by handover / another road / claims, not guaranteed). Maps saved in the Map Editor before this change keep their old gates (a new map version seeds the new zones).

## 72. Zones are rectangles you drag, resize and rotate; Line gates have a direction (user request; design in `docs/design/zone-editing.md`)
**Shape:** every Map Editor zone has a `shape` (`MapZone.shape`): a rotated **rectangle** `{kind:'rect', cx, cy, w, h, rot}` (metres, radians, 0 = +x, counter-clockwise) or a **Line gate** `{kind:'gate', a, b, depth, side}` (a line a -> b; the area is the line grown `depth` metres to `side`, +1 = left of a -> b, the side robots come from). `polygon` is DERIVED from the shape (`model/shape.ts polygonOf`) and is what the simulator, the Live Floor, thumbnails and the audit read, so they did not change. Pure geometry: `src/core/rect.ts` (`fitRect` = smallest rotated rectangle around any polygon, `rectCorners`; also used by `core/junctions.ts`, so the 60 junction zones in `nav.json` are rectangles now) and `features/map-editor/model/shape.ts` (`resizeRect` keeps the opposite corner / edge fixed, `rotateRectTo`, `gateRect`, `flipGate`, `gateFromThin`, `newGate`, `rectFromCorners`). **Everything saved is converted on load** (`normaliseData` -> `normaliseZone`): any polygon becomes the rectangle around it, a thin old line gate (`props.shape: 'line'`) becomes a gate 3 m deep; published versions included (user decision). Defaults: depth 3 m (`DEFAULT_DEPTH`), editable.
**Editing:** the selected zone of a draft shows its handles (`canvas/layers/ZoneHandles.tsx`, drawn by `ZoneLayer`): drag the body to move, 8 squares to resize (a corner keeps the opposite corner; Shift keeps proportions), the round handle on the stick to rotate (Shift snaps to 15 degrees); a Line gate has a handle on each end of its line and an arrow (click the arrow to flip the side). Sizes are pixels (bigger on touch). A drag is ONE undo step (`edit(fn, 'shape:<id>')`). Sidebar (`ZoneForm` / `ShapeFields`): rectangle = Centre X / Y, Width, Height, Rotation in degrees; Line gate = Start X / Y, End X / Y, **Depth (m)**, Direction (Flip). Keyboard (`useEditorShortcuts`): arrows nudge the selected zone 0.1 m (Shift 1 m), Delete asks to remove it, Ctrl+Z / Ctrl+Shift+Z as before. **Robots:** `TrafficZone.gate?: {a, b, depth, side}` (core/types). A zone without `gate` is a plain traffic zone (one robot at a time, section 70). A **Line gate** holds only robots that come from its controlled side (they move towards the line: `core/gate.ts comesFromGateSide`): such a robot waits at a hold point until the WHOLE area is clear (any robot inside counts, including one going the free way), then takes the gate like a zone; robots coming from the other side never ask for it and cross freely (their bodies are still kept apart by the physical check). `adapters/sim.ts entriesOf` drops gate spans whose path does not move towards the line, `takeEntry` adds the robots standing in the area; `RulesIndex.traffic` counts only controlled-side robots at a gate; the Live Floor draws the line and arrow (`rulesLayer.gateMarks`) and no-go zones from their polygon (not their bounding box). `applyPublishedMaps` now also passes `gate` and takes the maps' no-go zones (section 71). `derive:zones` keeps hand-made gates.

## 91. Importing a big v5 map: streamed grid, roads, staging areas (user request: `TBR_ROTR_YOHT.zip` said "zip is too large when opened")
**Root cause:** `yelli_map.npz` of that map inflates to a 28,836 x 21,322 byte grid, 615 million cells (99% empty, so 6 MB zipped). `readGrid` inflated the whole array into memory and was refused by the 300 MB zip limit (and the 256 million cell array limit behind it). **Fix (`map-import/core/pool.ts`):** the `.npz` is inflated as a stream (fflate `Unzip`) and every chunk is folded straight into a pooled picture (each factor x factor block keeps its strongest level; factor = smallest power of two that fits 16 million cells, 8 here, so 16 cm). Memory is the pooled picture, whatever the grid size; 3 s for the sample, in the worker. Speck clean-up scales to the pooled size (min 3 cells). The review says "drawn at 16 cm detail instead of 2 cm" (`grid.coarse`). A grid that is not a 2D table of bytes still goes the old way (`readNpy`); beyond 2^31 cells is refused.
**Grid orientation (`core/orient.ts`):** the v5 export stores the grid with axis 0 = x and axis 1 = y pointing up (the first sample had rows = y down). `map_origins` is always [x cell, y cell]. The file does not say which, so `detectOrientation` tests the path the robot drove (else stations and roads): the right way round puts it on free floor with a wall within 3 m; `rows-y` (the old convention) wins ties. Verified against the file's own `webui_map_preview.webp`.
**More of the zip is read now (`formats/deploymentManager/v5.ts`):** `gmaj.json` / `grid_map_attributes.json` hold the REAL station names, positions and headings (`webui_map.json` only has "Station n" at the origin: those stations used to be "Needs placement"): stations take them (heading radians -> degrees, `orientation: on_lane` -> On route, a name like PARKING -> parking type; every other field under `extra.gmaj`). Lines become **roads** (137 here -> 137 roads, 181 lanes = the file's 181 lines: a two-way road is one line, its reverse copy in `grid_map_attributes.json` is not a second road; direction, heading and the source fields kept in `MapRoad.extra`; ends join within 0.3 m, stubs under 1 m accepted: `addRoad` options `snap`, `allowShort`). `staging_areas.json` becomes staging areas: in the file x, y is the CORNER, ours is the centre of A1 (half a cell in; checked against the file's own cell station poses), cells have **gaps** (`StagingAreaDef.rowGap/colGap`, used by `cellCenter` / `outline`), FIFO / LIFO, sherpa type (`pallet_mover` -> Pallet Mover), source data under `extra.dm`; ids `SA-00n` above every area id of every map. `graph_object_v5.json` (derived from the lines), `ez.json` (no gates in the sample), `map_features.json`, `yelli_frames.npy` and the pictures are known files, not "unread". **Export** also writes name / pose / tags of edited stations back into `gmaj.json` and `grid_map_attributes.json` (untouched when nobody changed an angle) and keeps the v5 fields out of `webui_map.json`; roads, zones and areas still travel in `ati_flow/map.json`, `staging_areas.json` is not rewritten.

## 93. Compatible with the Deployment Manager: v5 write-back and v2 (point-to-point) import (user request: "100% compatible, the original features must remain")

## 94. v2 (point-to-point) maps have their own editing flow (user: "in v2 you create stations, make connections between them in routes, double-click a route to create nodes that bend it")

**Making routes (user: "clicking a station with routes selected selects the station"):** with the Routes tool armed on a p2p map a press on a station is a route end (`usePointerTools.startDrag` calls `onPoint`), not select / move; Shift- or Alt-click selects the station and keeps the tool armed (`pick(sel, { keepTool })`); the station form has **Add route from here** (arms the Routes tool with that station as the start). ## 98. Staging area properties in plain words (user request; supersedes the Sherpa type of sections 50 and 82)
**Removed:** Sherpa type (`StagingAreaDef.sherpaType`; saved maps drop it on load, the importer no longer reads `sherpa_type`, the export leaves the file's value alone). **Added to `StagingAreaDef`:** `cellAngle` (deg, limited to -60..60 by `clampCellAngle`: the form and the handle clamp it; every cell turns on its own centre), `stationOffset` (m, how far each cell's station stands in front of the cell, 0 = against it), `fill` (`CellSequence`: row / column by row, which row first, which cell first; default row by row from the first), `emptyBy` (`arrival` = oldest / newest first, the existing FIFO / LIFO `retrieval`; `position` = `emptyPosition`, a `CellSequence` too). Sequence maths is `core/cellOrder.ts` (`sequenceKeys`, `DEFAULT_SEQ`). Names on screen: **Width ↔** is `cellLength` (along the area direction) and **Length ↕** is `cellWidth`; gaps between columns / rows are `colGap` / `rowGap`.
**Drawing (`canvas/layers.ts stagingGeometry`, `MapLayers.tsx StagingLayer`):** every cell is a rotated rectangle, every cell has a station (ring + chevron, `stationPoint`: cell centre + (cellLength/2 + stationOffset) along the area direction, facing rotation + cellAngle). Column letters, row numbers and ONE orange arrow showing the cell direction appear only while the area is selected; the arrow's round handle (`StagingHandles`) turns the cell angle (Shift = 15 degrees). SVG units here are metres: sizes of text, handles and strokes that must stay the same on screen are written `n * u` (u = metres per pixel); a stroke width without `vectorEffect="non-scaling-stroke"` or `* u` is metres thick (this made the first arrow a giant orange blob).
**Files (`dm/stagingPatch.ts`, `v5.ts`):** `direction`, `station_offset`, `fill_by`, `fill_line_order`, `fill_cell_order`, `empty_by`, `empty_position_by`, `empty_line_order`, `empty_cell_order`, `arrival_order`; a key the file lacks is only added when it is not the default, so an unedited map still exports byte for byte. **Rules (`master-data/model/cells.ts`):** a drop uses the first free cell in the fill order (`freeCells`, `reserveDrop`), a pick follows arrival (FIFO / LIFO) or the position sequence (`pickOrder`, `planPick`, `chooseCells`). **Limits:** robots still drive to the area's entry station (the per-cell stations are drawn, not routed to), exported station poses in `grid_map_attributes.json` are still the cell centre, and the Master Data chip still says FIFO / LIFO when take-out is by position.
